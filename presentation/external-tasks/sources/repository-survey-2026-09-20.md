# Related medical imaging agent repositories

Surveyed 2026-09-20. Source task: [Survey similar medical repos](codex://threads/01a0bef4-b72c-7241-bb59-f5ca11d4db09). Author: assistant. This is source research and an assistant recommendation; it records no user decision to adopt a framework or launch an experiment.

**The closest practical comparisons are HealthAgentBench, ABRA, BCER, AutoMedBench, Imaging-101 and RadAgent.** MedOpenClaw/MedFlowBench is especially close to our full-study, auditable-evidence direction, but the linked public repository inspected here contains the project website rather than an identifiable runtime release. There is substantial overlap with our work. The useful question is which capabilities and evidence contracts tb3 can study more carefully.

The comparison uses the current [repository scope](../../../README.md), [workflow](../../../docs/workflow.md) and [governance](../../../docs/governance.md): agents inspect medical images, act through code or tools, produce spatial or quantitative artifacts, and undergo independent evaluation and evidence review. Current groups cover anatomy audit, landmarks, lesion localization, registration, tubular anatomy, cardiac motion and longitudinal reading. This excludes the archived nonmedical/security work.

**Search coverage and limits.** Broad web/GitHub searches covered medical imaging agents, terminal benchmarks, full-volume CT/MRI interpretation, viewer control, medical research automation, cardiac/echo measurement, segmentation, registration and coronary geometry. A community bibliography supplied discovery leads; substantive comparisons below use author repositories, project pages and papers. Twenty-eight selected projects are recorded below, including component libraries and projects with incomplete releases. This is a targeted broad survey, not an exhaustive systematic review. README/release claims were checked against repository contents where material; selected evaluator code was inspected. No external project was installed, run, clinically validated or independently reproduced. Model scores from different datasets/harnesses are not ranked against each other. Source metadata and selected Git blob identifiers are retained in the [survey receipt](../../../docs/evidence/medical-agent-repository-survey-2026-09-20.json).

**What the closer inspections establish**

1. **HealthAgentBench is directly relevant to our Harbor packaging.** The inspected [CT verifier](https://github.com/microsoft/HealthAgentBench/blob/main/tasks/ct_abnormality_valid_16_a_1/tests/harbor_evaluator.py) emits a binary success only when all retained labels match, while preserving detailed per-label metrics. Its README counts agent timeouts as zero-reward trials. For any comparison, retain that benchmark outcome alongside our separate execution/availability interpretation; do not equate timeout with a demonstrated medical-reasoning defect.
2. **ABRA provides a useful perception control.** Its [paper](https://arxiv.org/abs/2605.11224) reports at least 89% Execution for real annotation but 0–25% Outcome, versus 69–100% Outcome with oracle finding assistance. These are the authors' results, not reproduced here. The [scorer](https://github.com/Luab/ABRA/blob/main/src/scoring/base_scorer.py) weights planning/execution/outcome 20/30/50. We should preserve separate outcome metrics so successful navigation cannot obscure incorrect anatomy.
3. **BCER's contract is primarily about workflow completion.** Its [metric definitions](https://github.com/Albertlongzi/BCER/blob/main/docs/METRICS.md) and [runner](https://github.com/Albertlongzi/BCER/blob/main/benchmark/benchmark_runner.py) check required stage success and artifact validators such as nonempty NIfTI and affine agreement. Those are valuable execution guarantees, but do not independently establish correct anatomy or measurements. This is a concrete opportunity for complementary tb3 tasks.
4. **Assistance must be recorded per condition.** AutoMedBench's tiers, Imaging-101's supplied plans and RadAgent's specialist models change what the agent must infer itself. Their results should motivate matched experiments, not a pooled leaderboard with our current scans.

**What this means for tb3**

My interpretation is that our most useful focus is **controlled studies of what general agents can recover from native medical images, with physical output checks and reviewable evidence**. The combination is promising; this search does not establish that it is unique.

| Existing tb3 question | Most relevant comparisons | A concrete next research question |
| --- | --- | --- |
| Landmarks, anatomy and unavailable targets | ABRA, M3D, SpatialMed, Voxel | With the same image, how do raw-volume, viewer-tool and specialist-assisted conditions change physical localization and abstention? |
| Coronary identity and geometry | ImageCAS-X, HeuristicCLLabeling, VMTK; AMID reports for adjacent vascular tasks | Can the agent name branches better than a simple geometric heuristic when both receive the same unlabeled tree? Separately test discovery and path extraction. |
| Lesion localization and longitudinal reading | ABRA, HealthAgentBench, RadAgent, MedOpenClaw | Can the agent produce registered locations and measured change, with evidence that supports each statement? |
| Cardiac motion and quantitative interpretation | Cardiac Agent, EchoAgent, BCER | Does the agent select measurable frames/views, preserve calibration and detect when a requested quantity is unsupported? |
| Registration | L2R, BCER, Voxel | Can it maintain coordinate contracts and produce anatomically valid transforms, not just complete the pipeline? |
| Reconstruction / possible future ML engineering | Imaging-101, AutoMedBench, ReX-MLE | Is a failure in physical modeling, implementation, validation or learned-model training? This would broaden the present scope. |

I recommend an assistance matrix with three explicit conditions: (A) general agent plus generic image/code operations; (B) the same agent plus declared specialist tools; (C) a classical or specialist method with a fixed interface. Add supplied-reference/oracle conditions only as diagnostic controls. Keep model, case, time budget and reference version matched. These are proposed designs, not authorized trials.

Evaluation should retain distinct axes: task output correctness; physical geometry or measurement error; completeness and abstention; evidence support; execution status; resource use. Process traces can explain outcomes, but should not substitute for them. On the same coronary result, proximity, extent and branch identity can disagree; on registration, overlap and deformation plausibility can disagree. A single aggregate would hide exactly the distinctions our work is trying to understand.

**Suggested reading/reuse order.** Start with HealthAgentBench for compatible task packaging, ABRA for perception-versus-operation controls, and BCER for artifact contracts. Then inspect Imaging-101 and AutoMedBench for task construction and process evaluation. Choose RadAgent, Cardiac Agent or EchoAgent only for a matching modality and a clearly labeled specialist-assisted comparison. For the current coronary branch idea, inspect HeuristicCLLabeling before building another agent-specific method. Follow MedOpenClaw's runtime release and AMID's system release as reopening conditions.

Practical first follow-up would be a source-only comparison of one ABRA annotation task, one HealthAgentBench CT task and one of our landmark/vessel tasks: input visibility, available tools, reference independence, physical coordinate contract, output schema and timeout treatment. This can be done before installing any environment or spending model budget.
