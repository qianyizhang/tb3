# Evidence explanation review cases

Use these when revising the skill, with pinned raw artifacts and the actual
requested conditions. The reviewer should see the task before the criteria.
Record what was observed; structural checks alone do not establish recovery from
the earlier instruction regression.

| Case | Request and source | Observable criteria |
| --- | --- | --- |
| Stage versus cause | Explain an image-search failure using a frozen task, trace and actual crops. | Opens the relevant images, identifies consequential actions and source locators, separates the failed stage from context, reference, runtime and agent explanations, and records counterevidence or gaps. |
| Changed endpoint | Compare the retained WSI map and fixed-patch tasks. | Exposes supplied-location assistance and pixel-versus-patch units before interpreting scores. Does not rank models or average incomparable percentages. |
| Reference dispute | Explain disagreement with a sparse or partially annotated reference. | Shows relevant source/result/reference geometry, identifies the evaluated domain and keeps unannotated regions unassessed. Does not silently correct the original score. |
| Missing evidence | A manifest exists, but one consequential crop or trace segment is unavailable. | Names the unavailable evidence and narrows attribution. Does not claim visual inspection from a filename, generated plot or manifest hash. |

The owning WSI comparison and longitudinal trace findings are useful leads for
case selection in TB3. Pin the actual selected task/attempt/artifact identities;
do not assume their local availability or reuse an interpretation as raw evidence.
Fresh model-by-skill comparisons require separate execution scope and matched
conditions. These cases define maintenance checks, not a claim that they were run.
