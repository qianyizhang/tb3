01 / Why

A result needs a history.

A score alone cannot tell you what the agent saw, which condition ran, or whether the reference was sound. TB3 keeps those relationships inspectable so a useful result can survive later scrutiny.

Organize by question.

A group brings its ideas, methods, experiments, findings, and explanations together. Start with the scientific owner; the directory tree follows that ownership.

Preserve what happened.

Exact task snapshots and execution records anchor observations. A later replay, issue, or review adds context while preserving the original outcome.

Derive the reader’s view.

Shared Python code validates records and builds their current state. Static browser views make that state understandable without becoming another research database.

Why files, shared services, and static pages?

Small JSON, TOML, and Markdown records can be inspected, linked, versioned, and reviewed alongside the code. Large scans, credentials, and raw execution outputs stay local. Python supplies the common rules that would otherwise drift between scripts.

The browser can then be rebuilt from those sources. Local development and serving tools exist, but there is no separate database or application server holding research state. A portable view is a snapshot of what was built; it does not monitor a live job.

Read the owning guides: ArchitectureGovernance

The aim: informative capability research, including qualified partial studies. Submission qualification is a separate promotion decision.

groups/ · datasets/

Groups own the scientific question and its ideas, methods, experiments, findings, and presentation. Dataset records describe sources, receipts, and access limits.

Boundary: an experiment defines its exact transformations and what the solver may see. Dataset provenance alone does not determine input visibility.

Python workbench

The common rules

src/tb3_medical/

The med CLI dispatches to ordinary modules. Core services load records and derive current state; workflow services manage task snapshots, executions, and observations.

Boundary: keep reusable behavior in its owning service. CLI parsing and storage primitives should not absorb scientific method logic.

Browser surfaces

A read-only projection

presentation/frontend/

The workbench browses research and evidence. The Task Explorer explains task definitions, inputs, outputs, and conditions. Stories explain a particular operation or finding.

Boundary: Python owns browser payload contracts and generated TypeScript. React controls the reading experience; it does not decide scientific verdicts.

External runtime

Where execution happens

Harbor · Docker · solver client

An authorized launch runs the declared task through the external runtime. Attempts retain execution identity; raw logs and payloads remain in local runtime directories.

Boundary: preparing, browsing, or explaining work does not authorize a model run. Transport or client errors are infrastructure observations, not demonstrated capability failures.

Packages & exports

A deliberate handoff

exports/ · local output destinations

Bundles use declared reproduction support; exports use recipes with pinned origins. A package includes a selected scope and provenance in a fresh destination.

Boundary: verifying bytes, replaying saved outputs, and executing a new model attempt establish different things. A draft package is not submission qualification.

The crucial boundary: what can the solver see?

The experiment/task contract owns visibility. A file’s role must remain explicit through preparation, execution, and presentation.

Solver-visible

Instructions, declared image inputs, permitted helper files, and available tools. These define the condition being tested.

Evaluator-only

Ground truth, oracle solutions, and scoring references. Reader reveals must label these roles; a helpful explanation must not silently become a solver input.

Later inspection may also use post-hoc diagnostics. Label them as such: they are neither the original solver input nor an original prediction.

Add a question or experiment condition
  1. Search the existing work with uv run med list 'your topic'. Read the owning group’s README and AGENTS.md.
  2. Use med idea for a question and med decide for a decision with its actual actor. Link prior work and reopening conditions.
  3. For a concrete condition, scaffold with med new GROUP ID --title "Title". Keep compact configuration beside the protocol in groups/<group>/experiments/<id>/.
  4. Specify inputs, allowed helpers, output contract, references, comparison limits, and execution/reproduction support.

Smallest useful change

An idea can remain an idea. A new condition can reuse an existing method; it need not introduce shared code.

Check

uv run med check validates authored records. That check does not execute the proposed study.

Add preparation, scoring, or inspection logic
  1. Place question-specific logic in groups/<group>/methods/<method>/, with explicit entry points and documentation.
  2. Reuse a supported method, or declare an authored task_path and explicit prepare_command. Preview with med prepare ID.
  3. Exercise the method with small synthetic inputs: answer shape, geometry/units, reference handling, and the behavior that could go wrong.

05 / Frequently asked

Questions you can stop carrying.

The distinctions that make the rest of the repository easier to read.

Getting oriented

Is this a benchmark, an app, or a research repository?

It is a research workbench with a CLI and a static reader. Tasks and scores are part of its evidence, but the organizing unit is the scientific question. Submission qualification is a separate promotion step.

Where should I begin if I only want to understand it?

Read the five-layer map, then follow one group’s README to a single experiment and its finding. Use med list 'topic' and med show ID. You do not need to understand every probe or historical round first.

Workbench overview, Task Explorer, and stories—why three?

The overview answers “what research and evidence exist?” The Task Explorer answers “what is this task and its input/output contract?” A story answers “how does this operation or explanation unfold?” They are different reader paths over source-backed material.

Do I need Docker, data, or model credentials just to read?

This guide needs only a browser and works offline. Generated static readers can also be browsed without the solver runtime. Building them requires the documented Python/Node setup; native image tours need their local data. Running a study has separate runtime and authorization requirements.

Understanding evidence

Why are execution, result, and review separate?

A process can fail before producing a scorable answer, an answer can receive a score, and a later review can question what that score supports. Collapsing these into “pass/fail” loses the reason. See the status vocabulary.

Does replaying saved output count as another model run?

No. Replay observes retained output under a recorded evaluation context. A fresh execution creates a new attempt. Both can be useful, but they support different claims.

If I fix a scorer or reference, should I change the old score?

Preserve the original outcome. Add the new observation or review with its provenance, affected scope, and limits. Technical defects need retained reproduction evidence; clinical/reference disputes require appropriate adjudication.

Does a polished visualization prove a task worked?

No. A symbolic illustration can explain the intended operation even when native images, predictions, or references are absent. Presentation checks verify the reader, not medical validity or agent capability. Label evidence gaps where the reader encounters them.

Making changes

Should this be a group method or shared Python code?

Start local when the method belongs to one question. Extract a shared helper when maintained methods demonstrate reuse. Extend an explicit method adapter only when the common operations require it; a new task does not automatically need a new abstraction.

Why did my frontend change not appear?

The browser reads generated output. Rebuild stale frontend bundles, rebuild the static view when source data changes, and restart the development snapshot after Python/source-record changes. Do not treat the generated page as the source to edit.

Can I delete old probes or raw runs once the guide is updated?

An updated explanation does not replace evidence. Historical probes may anchor exact task bytes and original outcomes; raw outputs have their own retention and recovery requirements. Use the bounded artifact-retention workflow for an explicitly owned scope.

How is this developer guide different from a canonical task explainer?

This file explains repository responsibilities. It has no task binding, patient data, scoring logic, or research-state writes. Task explainers belong in the existing brief/story pipeline so they retain source roles, contracts, review receipts, and export behavior.
